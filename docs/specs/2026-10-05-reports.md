# Account Reports — Build Spec

- **Date:** 2026-10-05
- **Status:** Draft for review — defines the target reporting behavior to build
- **Scope:** Account-level reporting engine concepts, report definitions, filters, metrics, calculations, presentation, and acceptance criteria
- **Primary outcome:** A user can open one account and understand what money came in, where money went, how flexible their spending is, and how household income is shared.

---

## 1. Reporting goals

### 1.1 Product goals

The reporting experience should:

1. Make each account's money movement immediately understandable.
2. Use one consistent period model across reports.
3. Make every total explainable from the rows or chart segments beneath it.
4. Distinguish personal-account and joint-account reporting clearly.
5. Present numbers in a calm, mobile-first reporting surface rather than a bookkeeping ledger.

### 1.2 Version 1 success criteria

Version 1 is successful when:

- all report totals use the same transaction-date and account-scope rules;
- period-based summaries agree with their supporting report rows;
- users can move between calendar months without losing report context;
- every chart has a readable numeric alternative or summary;
- personal, joint, empty, and zero-data states are explicit;
- reports remain understandable without requiring the user to understand the underlying data model.

## 2. Reporting scope

### 2.1 In scope

Version 1 includes these reports:

1. **Reports Overview**
2. **Income vs Expense Trend**
3. **Category Breakdown**
4. **Contribution Split**
5. **Fixed vs Variable**

It also includes:

- account context;
- selected-period filters;
- calendar-month stepping;
- rolling trend spans;
- consistent metric definitions;
- empty and zero states.

### 2.2 Out of scope for version 1

- Cross-account or household-wide consolidated reporting
- Budget vs actual reporting
- Forecasting or cash-flow projection
- Custom report builders
- Saved report views
- Export or scheduled delivery
- Tax reporting
- Recurring-transaction detection
- Multi-currency conversion

## 3. Core reporting model

### 3.1 Account scope

Every report must be scoped to exactly one selected account.

Version 1 must not mix multiple accounts into one report. The account is an immutable report context, not a user-changeable report filter inside the report page.

### 3.2 Access rule

A viewer may open reports for an account when either condition is true:

1. they own the account; or
2. the account is marked joint.

There is no separate report-level permission in version 1.

### 3.3 Reporting grain

The reporting grain is the transaction record.

A transaction is reportable only when all of the following are true:

1. it belongs to the selected account;
2. it is not deleted;
3. its transaction date falls within the report period;
4. its transaction type qualifies for the selected report;
5. any additional report-specific eligibility rule is satisfied.

Reports must use the transaction date, not the record creation or update date.

### 3.4 Transaction-type treatment

| Transaction type | Report treatment |
|---|---|
| Income | Counts toward income and contribution metrics |
| Expense | Counts toward spending, category, and fixed/variable metrics |
| Transfer | Does not count as income or spending |

Transfer fee rows must be treated as expenses when they satisfy the same reportability rules as ordinary expense transactions.

### 3.5 Effective category

To keep report totals reconcilable, every expense must resolve to an effective category value:

1. If it has a category, the effective category is that category.
2. If it has no category, the effective category is **Uncategorized**.

Category reports must not silently omit uncategorized spending from grouped totals.

## 4. Report request model

The reporting engine should be driven by a standardized report request rather than bespoke report logic.

### 4.1 Request inputs

| Input | Required | Purpose |
|---|---|---|
| Account | Yes | Identifies the single reporting scope |
| Report ID | Yes | Selects one report definition |
| Period start / end | Required by period reports | Defines the selected transaction-date range |
| Trend months | Required by trend reports | Defines the rolling calendar-month span |

### 4.2 Report result contract

Every report result should expose:

1. the report ID;
2. the exact effective period;
3. the account context;
4. report totals;
5. grouped rows, time-series rows, or both;
6. each row's metric values and percentages;
7. enough metadata for the UI to know whether the report is empty or non-empty.

The UI must not recompute a core metric in a way that can disagree with the report result. Client-side work is limited to presentation, such as formatting, reversing rows for display, or summing values that are explicitly presented as totals.

### 4.3 Shared calculation standards

| Rule | Requirement |
|---|---|
| Income | Sum of qualifying income amounts |
| Expense | Sum of qualifying expense amounts |
| Net | Income − expense |
| Share | Row amount ÷ applicable base total × 100 |
| Zero data | Treat missing sums as `0`, not `null` |
| Rounding | Percentages retain two-decimal precision until display |
| Currency display | IDR, `id-ID`, no visible decimal fraction |
| Time basis | Local transaction dates within local period boundaries |

Displayed percentages may be rounded for presentation, but the report must state or imply the correct base total so users can understand how each percentage was derived.

## 5. Period and filter requirements

### 5.1 Selected period

The selected period applies to:

1. Reports Overview summary and categories;
2. Category Breakdown;
3. Contribution Split;
4. Fixed vs Variable.

Requirements:

1. The default selected period is the current calendar month.
2. The UI must support previous-month and next-month stepping.
3. The UI must support an explicit start and end date.
4. Start date must be earlier than or equal to end date.
5. Invalid or reversed ranges must be rejected inline.
6. Moving to the previous or next month must select the complete previous or next calendar month.
7. Period changes must preserve the account context and report destination.

### 5.2 Trend span

The trend span applies only to Income vs Expense Trend and the overview's trend preview.

Requirements:

1. The engine accepts rolling spans from 1 to 24 months.
2. The trend page exposes 3, 6, and 12 months.
3. The selected span always ends with the current calendar month.
4. The current partially completed month is included.
5. The overview's trend preview remains fixed at six months unless the report definition explicitly changes later.

### 5.3 Explicitly excluded filters in version 1

The reporting UI must not offer:

- multi-account selection;
- category selection;
- transaction-type selection;
- contributor or member selection;
- amount-range filtering;
- saved filters;
- comparison-period filters.

These may be added later, but version 1 should keep filters focused and predictable.

## 6. Report definitions

### 6.1 Reports Overview

**Purpose:** summarize the selected period and route the user into focused reports.

#### Required structure

1. Account name and reports title
2. Selected-period summary: Income, Expense, Net
3. Last six months income-vs-expense preview
4. Top Spending Categories for the selected period
5. Links to focused reports

#### Metrics

| Metric | Base | Definition |
|---|---|---|
| Income | Selected period | Sum of income |
| Expense | Selected period | Sum of expenses |
| Net | Selected period | Income − expense |
| Top categories | Selected period | Expense grouped by effective category |
| Trend preview | Last six calendar months | Monthly income and expense |

#### Behavior

1. The selected-period summary must describe the same period as the top-categories section.
2. The six-month preview must be labeled as a six-month view so it is not mistaken for selected-period data.
3. The overview must show the top five categories only.
4. The full category report must show all effective categories.
5. Net must use positive/negative color semantics.

#### Acceptance criteria

- Selected-period summary equals the sum of the selected-period transactions defined by the report model.
- Category totals reconcile to selected-period expenses, including Uncategorized.
- Changing the selected month changes the summary and top categories.
- Changing the selected month does not silently change the six-month trend preview.

### 6.2 Income vs Expense Trend

**Purpose:** show monthly income, spending, and surplus over a configurable period.

#### Required structure

1. Range selector: 3M, 6M, 12M
2. Grouped monthly income-vs-expense chart
3. Total Income, Total Expense, and Net cards
4. Monthly breakdown table

#### Metric definitions

| Metric | Definition |
|---|---|
| Month income | Sum of income in that calendar month |
| Month expense | Sum of expenses in that calendar month |
| Month net | Month income − month expense |
| Surplus rate | Month net ÷ month income × 100 when income is greater than zero |
| Zero-income surplus rate | `0` |
| Total income | Sum of monthly income across the selected span |
| Total expense | Sum of monthly expense across the selected span |
| Total net | Total income − total expense |

#### Row ordering

1. The chart must display months chronologically, oldest to newest.
2. The table must display months reverse-chronologically, newest to oldest.

#### Surplus-rate interpretation

| Surplus rate | Status |
|---|---|
| 20% or higher | Healthy |
| 0% to below 20% | Warning |
| Below 0% | Negative |

#### Acceptance criteria

- 3M, 6M, and 12M return the correct number of calendar months.
- The current partially completed month appears as the newest month.
- A month with zero income shows a zero surplus rate, not an error.
- Total cards reconcile with the monthly rows.

### 6.3 Category Breakdown

**Purpose:** show spending concentration by category and expose the largest spending “leaks.”

#### Filters and grouping

| Configuration | Requirement |
|---|---|
| Base records | Expenses |
| Period | Selected period |
| Grouping | Effective category |
| Sort | Category total descending |
| Tie-break | Category name ascending |
| Overview limit | Top five |
| Dedicated report limit | All effective categories |

#### Metric definitions

| Metric | Definition |
|---|---|
| Category total | Sum of expenses assigned to the effective category |
| Category share | Category total ÷ selected-period expense total × 100 |
| Period total | Sum of all selected-period expenses |

The sum of all category rows, including Uncategorized, must equal the period total.

#### Presentation

1. Donut chart showing category composition.
2. Ranked list showing category name, amount, and share.
3. Category color and icon from category decoration data.
4. A fallback visual treatment for Uncategorized.
5. Empty state when no expenses exist in the selected period.

#### Accessibility and clarity requirements

1. The chart must not rely on color alone.
2. Every visible slice must have an equivalent row with name, amount, and percentage.
3. The period total must be visible or reachable without ambiguity.

#### Acceptance criteria

- Uncategorized expenses appear in the report as Uncategorized.
- Visible category rows reconcile to the displayed period total.
- The dedicated report is not limited to the overview's top-five slice.
- The empty state appears only when there are no reportable expenses.

### 6.4 Contribution Split

**Purpose:** show how joint-account income is contributed by the people responsible for income records.

#### Eligibility

| Account type | Required behavior |
|---|---|
| Joint | Show contribution breakdown |
| Personal | Show a “Joint accounts only” empty state |

#### Contributor model for version 1

Version 1 must infer contributors from the creator of each qualifying income transaction.

Requirements:

1. A contributor appears only when they created qualifying income in the selected period.
2. There is no separate household-member roster in version 1.
3. Contributor grouping must use a stable contributor identity, not display name alone.
4. If contributor metadata cannot be resolved, the income must be grouped under an **Unattributed** contributor row.
5. Unattributed income must remain part of total income and contributor reconciliation.

#### Metric definitions

| Metric | Definition |
|---|---|
| Member contribution | Sum of qualifying income created by that member |
| Member share | Member contribution ÷ total qualifying income × 100 |
| Total income | Sum of all qualifying income for the selected period |

#### Sorting and color assignment

1. Sort contributors by contribution descending.
2. Break ties by stable contributor identity, then display name.
3. Place Unattributed after identified contributors.
4. Assign visual colors only after final sorting.
5. Colors must not be the only way to identify a contributor.

#### Presentation

1. Horizontal stacked contribution bar.
2. Legend with contributor name, contribution amount, and percentage.
3. Total income below the legend.
4. Empty state when a joint account has no qualifying income.
5. Personal-account state when the report is not eligible.

#### Acceptance criteria

- Personal accounts never render contribution metrics.
- Member shares reconcile to the displayed total.
- Equal contributions receive a deterministic visual order.
- No contribution data produces a clear empty state rather than a blank chart.

### 6.5 Fixed vs Variable

**Purpose:** show how much spending is committed, how much is flexible, and how much still needs classification.

#### Classification model

Every reportable expense must resolve to one effective spend class:

| Class | Rule |
|---|---|
| Fixed | Category is marked as fixed cost |
| Variable | Category exists and is not marked as fixed cost |
| Uncategorized | Expense has no category |

Uncategorized must be shown as its own segment or summary row. It must not be silently folded into Fixed or Variable.

#### Metric definitions

| Metric | Definition |
|---|---|
| Fixed total | Sum of expenses in fixed-cost categories |
| Variable total | Sum of expenses in non-fixed categories |
| Uncategorized total | Sum of expenses without a category |
| Grand total | Fixed total + variable total + uncategorized total |
| Fixed share | Fixed total ÷ grand total × 100 |
| Variable share | Variable total ÷ grand total × 100 |
| Uncategorized share | Uncategorized total ÷ grand total × 100 |
| Spending flexibility | Variable share |

#### Presentation

1. Composition bar with Fixed, Variable, and, when present, Uncategorized segments.
2. Fixed and Variable total cards.
3. Uncategorized total or prompt when applicable.
4. “Spending Flexibility” percentage based on Variable share.
5. Empty state when there are no reportable expenses.

#### Flexibility interpretation

| Variable share | Status |
|---|---|
| 50% or higher | Healthy flexibility |
| 25% to below 50% | Reduced flexibility |
| Below 25% | Low flexibility |

When uncategorized spending is present, the UI should communicate that the flexibility number may improve after categorization.

#### Acceptance criteria

- Fixed, Variable, and Uncategorized rows reconcile to the grand total.
- Uncategorized expenses cannot disappear from the report total.
- A zero-expense period shows the empty state.
- Flexibility status follows the defined thresholds exactly.

## 7. Report configuration matrix

| Report | Base records | Period | Grouping | Required metrics | Main visualization |
|---|---|---|---|---|---|
| Reports Overview | Income and expense | Selected period plus fixed six-month preview | Month; effective category | Income, expense, net; monthly trend; category totals and shares | Period cards; grouped bars; donut/list |
| Income vs Expense Trend | Income and expense | Rolling 1–24 month span | Calendar month | Monthly income, expense, net, surplus rate; span totals | Grouped monthly bars |
| Category Breakdown | Expense | Selected period | Effective category | Category total, category share, period total | Donut plus ranked list |
| Contribution Split | Income on joint accounts | Selected period | Stable contributor identity, with Unattributed fallback | Contribution, member share, total income | Stacked bar plus legend |
| Fixed vs Variable | Expense | Selected period | Fixed / Variable / Uncategorized | Class totals, class shares, grand total, flexibility | Composition bar plus stat cards |

## 8. Empty, zero, and edge behavior

| Situation | Required behavior |
|---|---|
| No transactions in period | Show period-specific empty state |
| Income is zero | Show zero income; net equals negative expense; surplus rate is zero |
| Expense is zero | Show zero expense; net equals income |
| No categorized expenses | Show Uncategorized row rather than omitting spending |
| No contributors | Contribution report shows no-income state |
| Personal account opens Contribution Split | Show “Joint accounts only” |
| Income has no resolvable contributor | Add an Unattributed contributor row and include it in total income |
| Invalid custom period | Reject inline and retain the last valid view |
| All values are zero | Render zero values explicitly; percentages are zero, not blank |
| One contributor only | Show a single 100% contribution segment |

## 9. Presentation requirements

### 9.1 Number display

1. Use IDR formatting with the `id-ID` locale.
2. Use no visible decimal fraction for monetary values.
3. Use tabular numerals for comparable figures.
4. Show percentages consistently, normally with no decimals in compact UI and up to two decimals where precision matters.

### 9.2 Color semantics

| Meaning | Required treatment |
|---|---|
| Income | Positive/success color |
| Expense | Expense/error color |
| Net | Positive color when zero or positive; negative color when negative |
| Fixed spending | Clearly distinct from variable spending |
| Uncategorized | Neutral or warning-like fallback, not invisible |

Color must never be the only carrier of meaning.

### 9.3 Accessibility

Every chart must provide one or more of the following:

1. a visible numeric legend;
2. a table equivalent;
3. a concise text summary;
4. non-color indicators for status.

Chart controls must have accessible labels, and status thresholds must be explained in plain language.

### 9.4 Responsive behavior

1. Reports must be mobile-first.
2. Summary cards must remain readable on narrow screens.
3. Tables must scroll horizontally only when necessary.
4. Charts must not force the page width beyond the viewport.
5. Period controls must remain reachable without excessive scrolling.

## 10. Reporting invariants

The implementation must preserve these invariants:

1. A report cannot include another account's transactions.
2. A deleted transaction cannot affect any report.
3. A transfer does not inflate income or spending.
4. A transfer fee can increase expense reporting.
5. Contribution totals include identified and Unattributed contributor rows.
6. Every period report records the exact period it used.
7. Every grouped total has a visible or derivable base total.
8. Category Breakdown includes Uncategorized as a first-class grouping.
9. Fixed vs Variable includes Uncategorized as a first-class class.
10. The same transaction cannot be counted twice within the same report.
11. Changing a period must never silently change the six-month trend preview's meaning.

## 11. Acceptance checklist

Before the reporting build is considered complete:

- [ ] Reports overview uses selected-period summary cards.
- [ ] Reports overview labels the six-month preview explicitly.
- [ ] Trend supports 3M, 6M, and 12M.
- [ ] Trend monthly rows reconcile to span totals.
- [ ] Category report includes Uncategorized.
- [ ] Category rows reconcile to the expense period total.
- [ ] Contribution report is personal-ineligible and joint-only.
- [ ] Contribution shares reconcile to income total.
- [ ] Contributor ordering and color assignment are deterministic.
- [ ] Unresolved contributors appear as Unattributed without reducing total income.
- [ ] Fixed vs Variable includes an Uncategorized class.
- [ ] Fixed, Variable, and Uncategorized totals reconcile to the grand total.
- [ ] Empty states are implemented for all reports.
- [ ] Invalid date ranges are handled inline.
- [ ] Currency, percentage, date, and status formatting follow this spec.
- [ ] Charts provide accessible numeric equivalents.
